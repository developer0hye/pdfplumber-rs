# Errors and resource limits

This guide distinguishes the error and resource behavior of pinned Python
`pdfplumber` v0.11.10 from this project's current Rust library, Python
adapter, Command-Line Interface, and WebAssembly surfaces. Similar operations
do not imply identical exception types, diagnostics, budgets, or recovery
behavior. This is an operations and migration reference, not a compatibility
declaration.

| Surface | Public failure form | Caller-configurable resource controls |
| --- | --- | --- |
| Pinned Python `pdfplumber` | Python exceptions, warnings, and log records | None |
| Current Rust library | `Result<T, PdfError>` plus `Page::warnings()` | `ExtractOptions` |
| Current Python adapter | Python exceptions translated from Rust or generated by argument handling | None |
| Current Command-Line Interface | Standard-error text and process status | None |
| Current WebAssembly adapter | JavaScript `Error` through `JsError` | None |

## Pinned Python error behavior

Pinned Python `pdfplumber==0.11.10` defines two library exception classes:
`PdfminerException(Exception)` and `MalformedPDFException(Exception)`. Both
derive directly from `Exception`; neither is a `RuntimeError`, `ValueError`, or
subclass of the other.

### Library exceptions

`PdfminerException` is the boundary around failures from `pdfminer.six` while
opening a document, enumerating pages, or interpreting page layout. The
constructor receives the original exception object, so the wrapper wraps the
original exception as its sole argument and the wrapper's string is the wrapped
exception's string. The wrapped object remains available in `error.args[0]`;
Python exception chaining is not used by this code path.

For example, an empty byte stream raises `PdfminerException` whose sole
argument is a `PDFSyntaxError`. Its rendered text is exact:

```python
from io import BytesIO

import pdfplumber
from pdfplumber.utils.exceptions import PdfminerException

try:
    pdfplumber.open(BytesIO(b""))
except PdfminerException as error:
    assert str(error) == "No /Root object! - Is this really a PDF?"
    assert type(error.args[0]).__name__ == "PDFSyntaxError"
```

In the pinned password fixture, missing and incorrect passwords both raise
`PdfminerException` with an empty message. Type and message alone therefore do
not distinguish “password required” from “password incorrect.” The original
`PDFPasswordIncorrect` object is the sole argument in both cases. Never echo a
candidate password while adding application context.

`MalformedPDFException` covers malformed structures handled inside
`pdfplumber`: examples include non-numeric page boxes, recursion while
resolving PDF objects, and a PDFium failure while creating a `PageImage`.
These errors are separate from a top-level `PdfminerException` and from normal
argument validation.

### Validation, warnings, and repair

For callers, argument and geometry validation can raise ordinary `TypeError`
and `ValueError`; these errors are not normalized to either library exception. For
example, invalid table strategies and invalid crop boxes raise `ValueError`,
while a Python call shape can raise `TypeError` before the method body runs.
Decoding and library internals may also expose more specific built-in errors.

Metadata behavior depends on an open argument. `strict_metadata=False` logs a
warning and retains the unresolved value when metadata decoding fails.
`strict_metadata=True` re-raises the underlying metadata exception; the
committed cyclic metadata case raises `RecursionError`. Annotation decoding is
similar but uses Python warnings: `raise_unicode_errors=True` propagates
`UnicodeDecodeError`, while `raise_unicode_errors=False` emits `UserWarning`
and continues with degraded annotation data.

```python
import warnings

import pdfplumber

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    with pdfplumber.open(
        "annotations.pdf",
        raise_unicode_errors=False,
    ) as pdf:
        annotations = pdf.pages[0].annots
    # Inspect caught without treating a warning as full-fidelity output.
```

`repair=True` invokes Ghostscript before normal opening. In this path, repair
failures raise plain `Exception` with Ghostscript's standard error text. In
particular, the Ghostscript repair subprocess has no timeout, and the Python
library does not isolate its CPU or memory use. The
[encryption and repair guide](encryption-and-repair.md) defines the complete
supported behavior; this page records only failure and resource boundaries.

### No built-in resource budgets

The pinned `PDF.open` signature accepts the input, selected pages, layout,
password, metadata strictness, Unicode normalization, repair controls, and
Unicode-error policy. It has no input-byte, page-count, object-count,
image-byte, recursion, memory, or time budget. `pages=` is a one-based
selection filter, not a page-count budget: when `PDF.pages` is first read, it
still enumerates the complete `PDFPage.create_pages` generator and skips
unselected results rather than stopping after a maximum count.

Consequently, selecting one page does not establish an input-size, parse-time,
page-tree, or memory ceiling. A caller handling untrusted documents must add
host-level controls rather than assuming the Rust options described below are
present in Python.

## Rust errors and warnings

The high-level Rust facade returns an opaque `PdfError`. Classify it with
`PdfError::kind()` and
`PdfErrorKind::{Parse, Io, Font, Interpreter, ResourceLimit, PasswordRequired, InvalidPassword, Other}`.
Their stable codes are `PARSE`, `IO`, `FONT`, `INTERPRETER`, `RESOURCE_LIMIT`,
`PASSWORD_REQUIRED`, `INVALID_PASSWORD`, and `OTHER`. Always match the
non-exhaustive enum with a wildcard so a future category does not break the
caller.

| Kind | Present meaning | Typical caller action |
| --- | --- | --- |
| `Parse` | PDF syntax, structure, or object resolution failed | Reject or explicitly attempt the separate repair path |
| `Io` | A path or reader operation failed | Check protected source diagnostics and input availability |
| `Font` | Font or encoding data could not be resolved | Record the affected operation/page and inspect protected diagnostics |
| `Interpreter` | Page content interpretation failed | Record page/object context; do not classify it as a parse or limit error |
| `ResourceLimit` | One of the four wired optional budgets was exceeded | Inspect typed limit fields; use a smaller input or a reviewed larger budget |
| `PasswordRequired` | A non-empty password is required | Retry through a password-aware open method |
| `InvalidPassword` | The supplied password did not decrypt the document | Ask for another credential without logging the attempted value |
| `Other` | No narrower stable category applies | Treat as non-retryable unless application evidence says otherwise |

`PdfErrorContext` carries an operation, zero-based page index, and PDF object
number and generation when the facade knows them. `PdfResourceLimit` carries
`name`, `limit`, and `observed`; it is present for a typed resource failure.
Do not parse the `Display` text to reconstruct either structure.

### Safe and protected diagnostics

For Rust, ordinary `Display` and `Debug` omit paths, document content,
passwords, and the source message. `Debug` reports the kind, safe context, optional typed limit,
and only whether a source exists. `std::error::Error::source()` is opt-in and
can expose sensitive parser or operating-system details. Send source chains
only to a protected diagnostic sink.

```rust
use std::error::Error as _;

use pdfplumber::{PdfError, PdfErrorKind};

fn report(error: &PdfError) {
    eprintln!("PDF failure [{}]: {error}", error.kind().code());

    if error.kind() == PdfErrorKind::ResourceLimit {
        if let Some(limit) = error.resource_limit() {
            eprintln!("budget={} limit={} observed={}", limit.name, limit.limit, limit.observed);
        }
    }

    // Send this only to a protected sink; never expose it by default.
    let _protected_source = error.source();
}
```

### Non-fatal extraction warnings

The related public types are `ExtractWarningCode`, `ExtractWarning`, and
`ExtractResult<T>`. `Page::warnings()` returns the warnings retained during
that extraction. `collect_warnings=true` retains warnings and `false` discards
them; it does not change a fatal `Result` error.

There are two important current gaps. `strict_mode=false` is the default but
the field is not consulted by extraction. `ExtractWarning::to_error()` is a
manual helper, not automatic strict-mode wiring; it produces
`PdfErrorKind::Other` with operation `strict warning escalation`. Likewise,
`RESOURCE_LIMIT_REACHED` is declared but no extraction path emits it. In this
model, a fatal limit breach returns `PdfErrorKind::ResourceLimit` rather than a
warning.

## Rust resource controls

Only controls read by the current extraction source are labeled enforced.
Defaults come from `ExtractOptions::default()`.

| Field | Default | Current status | Scope and check point |
| --- | --- | --- | --- |
| `max_input_bytes` | `None` | Enforced | Before parsing for byte input; while reading for reader/path input; before and after repair |
| `max_pages` | `None` | Enforced | After parsing obtains the document page count, before page geometry is cached |
| `max_total_objects` | `None` | Enforced | Shared, cumulative, post-extraction count on one `Pdf` |
| `max_total_image_bytes` | `None` | Enforced with `extract_image_data=true` | Shared, cumulative, post-extraction bytes stored on page images |
| `max_recursion_depth` | `10` | Enforced as interpreter failure | Before interpreting each nested Form XObject |
| `max_objects_per_page` | `100_000` | Declared, not enforced | Stored and serializable, but no extraction path reads it |
| `max_stream_bytes` | `100 MiB` | Declared, not enforced | Stored and serializable, but no extraction path reads it |

In this configuration, all four optional enforced limits are unbounded by
default. Applications must set them explicitly. The fixed default recursion ceiling remains active, but
its failure category differs from the optional budget failures.

### Opening limits

For `max_input_bytes`, byte slices report their complete length; readers stop
after at most `limit + 1` bytes, so an oversized or unbounded reader is not
drained merely to compute its full size. The typed `observed` value for that
reader case is therefore sufficient to prove the breach, not necessarily the
complete source length. Path input uses the reader behavior.

In the repair route, repair checks both the original input and the repaired
byte result. A repair that expands an accepted source above the same byte ceiling fails
when the repaired output is opened. `max_pages` is checked after parsing
discovers the document page count and before page geometry is cached. Both
failures use `PdfErrorKind::ResourceLimit` and include `name`, `limit`, and
`observed`.

### Document-wide cumulative limits

`max_total_objects` counts characters, lines, rectangles, curves, and images
produced by `Pdf::page`. The counter excludes annotations, hyperlinks, form
fields, words, tables, and derived edges; annotations, hyperlinks, form fields,
words, tables, and derived edges are not counted. For the image budget, only
bytes stored in returned `Image.data` values are counted. That storage is populated only when
`extract_image_data=true`; with the default `false`, the page-image byte debit
is zero.

`extract_image_content` and `extract_images_with_content` do not debit this
byte counter. The latter calls `Pdf::page` and can debit the
object counter, but the separately returned image content is outside the
current `max_total_image_bytes` accounting.

For totals, document-wide totals are charged after a complete page extraction.
Therefore, the extraction that crosses a total limit has already performed its page-local
work and these counters are not peak-memory guards. In addition, repeated pages
and failed over-limit attempts remain charged. The object counter is updated first; an
object-limit failure occurs before the image-byte counter is updated.

Under concurrency, parallel callers share atomic counters and the first failing
page is scheduling-dependent. `pages_parallel()` retains result order but does not
cancel other page work after a failure. Use separate `Pdf` values when workers
need independent totals, and include retries or repeated page access in each
budget.

### Recursion and declarative fields

At interpretation, page content starts at depth zero; nested Form XObjects
above depth 10 fail under the default `max_recursion_depth`. More precisely, the interpreter
rejects `depth > max_recursion_depth`. This returns
`PdfErrorKind::Interpreter`, not `PdfErrorKind::ResourceLimit`, and it has no
`PdfResourceLimit` details.

Do not rely on `max_objects_per_page` or `max_stream_bytes` for protection.
They are public fields with documented defaults and Serde representation, but
current runtime extraction does not read them. Their names and defaults are
not evidence of enforcement.

### Configuring the enforced budgets

```rust
use pdfplumber::{ExtractOptions, Pdf};

fn open_untrusted(path: &str) -> Result<Pdf, pdfplumber::PdfError> {
    let options = ExtractOptions {
        max_input_bytes: Some(32 * 1024 * 1024),
        max_pages: Some(200),
        max_total_objects: Some(1_000_000),
        extract_image_data: true,
        max_total_image_bytes: Some(64 * 1024 * 1024),
        ..ExtractOptions::default()
    };
    Pdf::open_path(path, Some(options))
}
```

These values are examples, not recommended universal thresholds. Choose them
from application fixtures and capacity tests. This library has no enforced
CPU-time, wall-time, process-memory, decoded-stream, page-dimension,
output-size, or table-complexity limit. The declared stream and per-page object
fields do not fill those gaps.

## Current adapter boundaries

Rust is the only current surface that accepts `ExtractOptions`. The other
surfaces use the Rust core but do not forward its resource configuration.

### Python adapter

In this boundary, the Python adapter passes `None` to every native open method.
Its compatible `PDF.open(...)` signature accepts upstream-style inputs and options, but the
Python adapter exposes no warning collection or resource-budget argument.
The native defaults still apply, including the fixed recursion ceiling and
unbounded optional totals.

At the translation boundary, parse and password failures are mapped to the
compatibility `PdfminerException`. `PdfIoError`, `PdfFontError`,
`PdfInterpreterError`, and `PdfResourceLimitError` live in private
`pdfplumber._native`; they are not top-level compatibility exports.
`PdfResourceLimitError` is not reachable through the current public
constructors because callers cannot supply a limit. The class and translator
exist for the native boundary but do not create a public budget control.

Unlike Rust's outer `Display`, Python compatibility exception messages may
contain parser, operating-system, or document-derived details. Treat the type,
message, arguments, warning text, and logs as potentially sensitive.

### Command-Line Interface

In this release, the Command-Line Interface has no resource-budget or timeout
flag. It uses default `ExtractOptions` and prints Rust's safe outer `Display`
to standard error for library-originated failures. For process behavior,
runtime failures exit with status 1; argument parsing is owned by Clap, which
presents its own usage diagnostics.
The current `--pages` selects work but is not a document page-count budget.

A missing local path is checked by the Command-Line Interface itself and the
diagnostic prints that path. Also, `--password` can be visible to shell history
or process inspection even though Rust error text does not echo the password.
Those host boundaries require application-specific protection.

```console
pdfplumber text untrusted.pdf --pages 1-5
# A library/runtime failure writes a diagnostic to standard error and exits 1.
```

### WebAssembly

WebAssembly calls `Pdf::open_bytes(data, None)` and converts the safe outer
`Display` to `JsError` for Rust PDF failures. Serialization errors also become
`JsError` using their own message. The wrapper exposes no resource, warning,
password, repair, or timeout control. Browser fetch size, worker lifetime, and
WebAssembly memory policies belong to the host application.

## Operational policy

For untrusted documents, apply controls at more than one layer:

1. In Rust, explicitly set every relevant enforced optional budget. Turn on
   image data only when required and remember that direct image-content reads
   are outside the cumulative byte counter.
2. Applications should run untrusted inputs in a process or worker with
   host-enforced memory and time limits. Terminate and replace that worker on timeout rather than
   assuming a library field can interrupt arbitrary parsing or allocation.
3. Bound input acquisition before calling the library. A network response,
   upload, decompression step, or Ghostscript repair can consume resources
   outside extraction accounting.
4. Process pages incrementally where the surface permits it. A page selector
   narrows requested output but is not automatically a parser or memory cap.
5. Classify Rust failures by `PdfErrorKind` and typed fields. In Python,
   preserve the concrete exception type for application policy without
   depending on unstable parser wording.
6. For ordinary diagnostics, do not log Python exception arguments, Rust
   source chains, passwords, paths, or document bytes to an unprotected sink. Use an application request
   identifier and safe category in ordinary logs; reserve sensitive details
   for access-controlled diagnostics.

The following Python pattern keeps the public message generic while retaining
the exception type for an internal counter:

```python
from pdfplumber.utils.exceptions import PdfminerException

try:
    process_pdf()
except PdfminerException as error:
    metrics.increment("pdf.failure", tags={"type": type(error).__name__})
    raise UserFacingError("The PDF could not be processed") from None
```

This pattern deliberately does not claim that all Python failures are
`PdfminerException`; callers must handle the built-in validation, Unicode,
repair, and host I/O failures used by their workflow.

## Claim boundary

This guide does not establish error compatibility between Python and Rust or
between any adapters; error and resource-limit documentation is not
compatibility evidence and does not approve a compatibility deviation.
DOC-012 changes no runtime behavior.

`PARITY-012`, encryption, repair, malformed-input, parser/font robustness,
fuzzing, security, performance, allocation, timeout, and complete strict-gate
tasks remain independent and open according to the PRD. Declared but
unenforced fields remain limitations, not completed safety controls. No score,
supported platform, package metadata, release artifact, or compatibility claim
is changed by this documentation.
